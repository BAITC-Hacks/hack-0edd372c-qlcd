# Интеграция frontend с backend

Контракт **API 1.2.0**, проверенный по текущим исходникам, OpenAPI, API-тестам и браузерным запросам. Версия каталога: **`87d082de8481`**. Исправления внесены в frontend и backend; CSV не изменён. Результаты проверок и ограничения собраны в [аудите](audit.md).

## Реальный контракт

`GET /health` возвращает:

```json
{
  "status": "ok",
  "profiles_loaded": 66,
  "dataset_version": "87d082de8481",
  "api_version": "1.2.0"
}
```

`GET /api/meta`: `profile_count`, массивы `cities`, `categories`, `event_formats`, `languages`, `dataset_version`. Текущие города: `Алматы`, `Астана`, `Зарубежье`.

`dataset_version` — первые 12 символов SHA-256 содержимого CSV после замены CRLF на LF. Это версия **данных**, а не алгоритма. Версия API доступна в `/health` и `info.version` документа OpenAPI; один и тот же CSV может использоваться разными версиями приложения.

`POST /api/recommend`, JSON:

```json
{
  "city": "Алматы",
  "event_date": "2026-10-10",
  "event_type": "корпоратив",
  "category": "Ведущий",
  "budget_kzt": 1500000,
  "duration_hours": 6,
  "language": "русский",
  "limit": 3
}
```

Правила запроса:

- `city`, `category`, `event_type` — строки, непустые **после** trim. Пробелы удаляются до проверки длины; неизвестное, но непустое значение может дать бизнес-пустоту.
- `event_date` — строка `YYYY-MM-DD` без времени и timezone, от **2026-09-23 до 2026-12-31 включительно**. Timestamp, datetime-строка, несуществующая дата и выход за окно дают 422.
- `budget_kzt` — строго JSON integer, `1..9007199254740991` (`2^53−1`). Строки, дробные числа, `true/false`, ноль и отрицательные значения не принимаются.
- `duration_hours` — положительное конечное JSON number либо `null`. Числовые строки, логические значения, `NaN`, `Infinity` и их строковые формы не принимаются.
- `language` — строка либо `null`; после trim пустая строка превращается в `null` и не задаёт языкового фильтра.
- `limit` — строго JSON integer от 1 до 3; по умолчанию 3. Frontend всегда отправляет 3.

Ошибки валидации возвращают HTTP **422**, `detail` — массив объектов только с `type`, `loc`, `msg`. Поля `input` и `ctx` не включаются: сырые нечисловые значения или исключения не должны ломать JSON-сериализацию ответа. Это относится и к нестандартным числам, которые JSON-декодер может принять перед валидацией.

| Руководство | Фактический backend | Нормализация frontend |
| --- | --- | --- |
| `/recommend` | `/api/recommend` | Префикс сохраняется proxy |
| `date` | `event_date` | UI `date` → `event_date`, без timezone-преобразования |
| `budget` | `budget_kzt` | UI текст → точное положительное целое |
| `duration` | `duration_hours` | Пустое → null; запятая → точка до преобразования в число |
| `matches_found` | `matches_found` | `matches_found` |
| `category_not_found` | `no_category_in_city` | `category_not_found` |
| `no_eligible_candidates` | `no_candidates_meet_conditions` | `no_eligible_candidates` |
| `summary` | `message` | Видно над успешной выдачей; пустые исходы объясняются русскими подписями по счётчикам, исходный message доступен в технических деталях |
| `trace.city_category` | `total_category_city` | `trace.total` |
| `trace.eligible` | `eligible_count` | `trace.eligible` |
| `trace.rejected` | `excluded_summary` | `trace.rejected`, без пересчёта |

Ответ также содержит `query` — нормализованный снимок запроса — и `dataset_version`. Адаптер сверяет `query` с отправленными условиями и использует версию данных при сравнении дат. В модели ответа версия допускает `null`; frontend принимает этот случай и сообщает об отсутствии версии. Текущий сервер передаёт её.

Карточка: `id`, `name`, `category`, `city`, `price_from_kzt`, `synthetic`, `city_imputed`, `price_imputed`, `explanation`, `match_factors: string[]`, `score: number`. Три признака происхождения — boolean. UI показывает синтетический профиль и предупреждения о восстановленных цене/городе из ответа сервера. `score` не отображается как рейтинг или вероятность. Порядок и объяснения не переписываются.

Frontend отклоняет дубликаты, больше трёх карточек, пустое объяснение, несовместимые типы, несоответствующий город/категорию/цену и противоречивые счётчики. `match_factors` принимает строки, включая новые `profile` и `relevant_profile`, без закрытого frontend-enum.

Языков, календарей, `max_hours` и полных описаний в карточках API нет. Их проверяет backend; интеграционные тесты сверяются с CSV. Браузер не выполняет дополнительную фильтрацию. Из `match_factors` нельзя восстановить индивидуальную причину отсутствия профиля в top-3.

## Семантика исключений

Сначала определяется категория в городе. Затем действует **первая сработавшая причина**, в порядке из `recommender.py`:

1. `booked` — занят на дату.
2. `over_budget` — стартовая цена выше бюджета.
3. `format` — формат не поддерживается.
4. `language` — запрошенный язык отсутствует.
5. `duration` — превышен `max_hours`, если он не null.

Каждый исключённый профиль учитывается один раз. Инвариант: `total_category_city = eligible_count + sum(excluded_summary.values())`. Backend использует Counter, поэтому причины без исключений отсутствуют. UI не создаёт для них строки с нулями. Подходящие профили за пределами top-3 не считаются исключёнными.

Для `matches_found` и frontend-запроса с `limit=3`: `len(results) = min(3, eligible_count)`, `eligible_count > 0`. API также разрешает limit 1/2 и использует переданный лимит. Для двух пустых статусов `eligible_count = 0`, `results = []`; наличие исходной категории различается по `total_category_city` и статусу.

`excluded_summary` агрегированный: в нём нет отсутствующих ID и персональных причин. При смене даты frontend показывает изменение состава и счётчика занятости, но не утверждает, что конкретный исчезнувший профиль обязательно занят: он мог перестать попадать в top-3. Индивидуальную занятость в контрольном E1/E2 дополнительно подтверждает CSV.

## Ранжирование и объяснения

`score = round(budget_headroom + language_fit + duration_fit + evidence_fit, 2)`:

- `budget_headroom = max(0, 30 × (1 − price_from_kzt / budget_kzt))`.
- `language_fit = 20`, если задан язык, иначе `0`; язык уже проверен жёстким фильтром.
- `duration_fit = 5` при незаданной длительности; `10` при заданной длительности и `max_hours = null`; иначе `min(15, 5 + 10 × max(0, max_hours − duration_hours) / max(max_hours, 1))`.
- `evidence_fit = 5 × has(profile) + 10 × has(relevant_profile)`: **0** без содержательного факта, **5** за конкретную особенность из описания, **15** за такую особенность, связанную с запрошенной категорией или форматом.

Сортировка: `(-score, price_from_kzt, id)`. Это детерминированная эвристика, не оценка вероятности успеха. Изменение кода при неизменном `dataset_version` может изменить порядок; повторяемость проверяется при одинаковых версиях кода и данных.

Извлекатель выбирает **законченный исходный фрагмент**: предложение или пункт списка. Он учитывает основы слов и признаки категории — опыт, состав коллектива, инструменты, репертуар, материалы, оборудование, вместимость, кухню и особенности исполнения. Само упоминание категории/формата не даёт бонуса. Для многокатегорийного профиля используется категория запроса.

Приветствия, слоганы и обнаруженные утверждения, способные подменить структурированные ограничения, исключаются. Произвольного среза на 180 символах больше нет. Цитата сохраняет формулировку источника и обозначена как особенность **из описания профиля**. Свободный текст не меняет цену, город, язык, длительность и календарь в жёстких фильтрах. `max_hours=null` объясняется как отсутствие заданного ограничения, а не обещание неограниченной работы.

Если конкретного сведения не найдено, explanation прямо сообщает об этом и опирается на параметры каталога. Бонус описания тогда равен нулю. Такие профили не скрываются, если проходят жёсткие условия.

## Проверка каталога при загрузке

CSV читается как UTF-8 с поддержкой BOM и стандартного quoting. Требуется точный набор **13 колонок**; порядок может отличаться:

```text
id, anon_name, categories, city, city_imputed, synthetic,
price_from_kzt, price_imputed, event_formats, languages,
max_hours, busy_dates, description
```

Загрузчик проверяет обязательные значения, уникальность ID, количество полей, списки через `|` без пустых/повторяющихся элементов, флаги `True/False`, неотрицательную целую цену в безопасном диапазоне JSON/JavaScript, конечную положительную длительность и календарные даты `YYYY-MM-DD` внутри окна каталога. Пустые `busy_dates`, `max_hours` и `description` разрешены согласно их смыслу.

Повреждённый CSV вызывает `DatasetValidationError` с путём, физической строкой, колонкой и причиной; приложение не запускается с частично испорченным каталогом. Дробная цена не округляется и не усекается, неверный флаг не превращается в false. Рабочий датасет остался неизменным.

## Живые примеры

Полные запросы и ответы из браузерных проверок: [api-examples.json](api-examples.json). Версию и условия прогона сопоставляйте с [аудитом](audit.md). Приложение не импортирует этот файл и не подставляет его содержимое вместо API.

Сценарий A: `total_category_city=10`, `eligible_count=5`; порядок **HK-88430 → HK-29829 → HK-27222**, score **60 → 56 → 54**. Старый backend-процесс может возвращать прежний порядок, поэтому нужно проверить `/health` и перезапустить сервер после обновления.

Сценарий B: `matches_found`, `total_category_city=2`, `eligible_count=2`, `excluded_summary={}`; ID `HK-39372`, `HK-90001`. У первого `price_imputed=true`, у второго `synthetic=true`. Объяснения различаются: более 1000 заказов ежемесячно / сезонные и привозные цветы, палитра мероприятия.

Сценарий C: `no_candidates_meet_conditions`, `total_category_city=10`, `eligible_count=0`, `excluded_summary={"booked":4,"over_budget":6}`. Нельзя утверждать, что все десять исключены по бюджету: календарь проверяется раньше.

Сценарий D: `no_category_in_city`, нулевые счётчики и пустые results. UI уточняет «в текущем каталоге», поскольку отсутствие записей не описывает весь рынок города.

E1/E2: число карточек меняется с 3 на 2, booked с 2 на 3; HK-80581 занят 16 октября по CSV. Особенность Нами — более 15 лет ведения мероприятий; приветственный слоган не используется.

В F у HK-64395 одновременно `city_imputed=true` и `price_imputed=true`. Характеристики различаются содержательно: панорамная локация / зал до 200 гостей, кейтеринг и парковка.

Дополнительный сценарий G для лайв-бэндов проверяет три профиля одинаковой цены. У HK-23752, HK-31819, HK-83709 теперь разные цитаты о составе — вокалисты, квартет, звукорежиссёр и клавишник. Различимость не обеспечивается подстановкой имени или разной стоимости.

## Состояние найденных дефектов

| Ранее найденная проблема | Текущее состояние и проверка |
| --- | --- |
| Общие объяснения B/F и одинаковые тексты лайв-бэндов | Исправлено извлечением конкретных свойств; регрессии сравнивают содержательные фрагменты без имён и цены |
| Приветствие Нами вместо специальности | Цитируется опыт более 15 лет; отдельная регрессия исключает слоган |
| Обрыв цитаты на 180 символах | Убран; тест длинной цитаты проверяет исходное предложение до конца |
| `duration_hours: "Infinity"` вызывал 500 | Конечность и тип проверяются, ошибки безопасно сериализуются; прямой API возвращает 422 |
| Обязательные строки из пробелов проходили модель | Trim выполняется до проверки; 422 указывает соответствующее поле |
| Слабая валидация CSV | Строгий загрузчик и временные повреждённые CSV в регрессионных тестах |
| Неясно, запущен ли новый backend с тем же каталогом | `/health` передаёт `api_version`; текущий API — 1.2.0 |
| Прямой локальный frontend мог не пройти CORS | Явные defaults и настраиваемый `CORS_ORIGINS`; обычный proxy продолжает работать |

Ошибка разбивки городов на символы и отсутствие imputed/version были исправлены ранее. Legacy-справочник frontend сохранён для совместимости; его использование сопровождается предупреждением об источнике. На текущем API этот путь не нужен.

Остаются границы данных и продукта:

- У **8 из 66** профилей извлекатель не находит достаточно конкретного признака: список в [аудите](audit.md#что-по-прежнему-ограничивает-решение). Вместо выдуманного отличия показано ограничение данных; бонус описания равен 0.
- Отсутствие буквальных дублей в 11 200 проверенных запросах не гарантирует одинаково высокое смысловое качество всех описаний и будущих каталогов.
- API передаёт агрегированные исключения; персональные причины отсутствия ID не доступны frontend.
- Публичного production-адреса нет. Рекомендуемая схема proxy описана в [frontend README](../frontend/README.md#production-маршрутизация). Для раздельного размещения backend поддерживает `CORS_ORIGINS`: HTTP(S) origins через запятую, заменяющие defaults localhost/127.0.0.1 на портах 3000/5173/4173. Пути, credentials и `*` не принимаются; конфигурация не заменяет проверку deployment.

Runtime LLM, эмбеддингов и дообучения нет. `semantic.py` извлекает исходные фрагменты детерминированно; frontend не выполняет AI-ранжирование. AI-агент использовался при разработке. Подключение runtime LLM не является обязательным условием текущего кейса.

## Проверка объяснений человеком

1. Открыть подбор через «Начать подбор» и прочитать полные тексты на ноутбуке и мобильной ширине.
2. Сверить цену, формат, язык и длительность со структурированными полями CSV; найденную цитату — дословно с описанием профиля. Условия подбора и заявления автора описания имеют разные источники.
3. Проверить пометки synthetic/imputed, смысл стартовой цены за мероприятие и отсутствие обещания бронирования.
4. Убрать имена **и цену**; проверить различия B/F/E и лайв-бэндов по материалам, вместимости, опыту и составу.
5. Убедиться, что выбрана полезная для услуги законченная характеристика, нет приветствия и обрыва мысли. Для бедного описания проверить честное сообщение о недостатке сведений.
6. Повторить запрос и сравнить порядок; затем выполнить E1/E2, проверить смену выдачи и агрегированный счётчик занятости. Не приписывать персональную причину всем исчезнувшим карточкам без календаря.

Автотесты подтверждают известные регрессии, происхождение фрагментов и отображение. Их успех не заменяет смысловую оценку жюри и не исправляет автоматически качество новых исходных данных.

## Безопасные ошибки и состояние

422 сопоставляется с полями по `detail[].loc`; произвольные raw `msg`, `input`, stack и секреты не показываются. Backend также исключает `input` и `ctx` из своего ответа. Frontend различает 404/405, 5xx, HTML, повреждённый JSON, сеть, таймаут и нарушение контракта.

Старые карточки скрываются при новом запросе и ошибке. AbortController вместе с номером запроса защищает сброс и новый запрос от запоздалого ответа. История содержит только предыдущий успешный запрос; скрытой подстановки рекомендаций при отказе API нет.
