# Интеграция frontend с существующим backend

Проверено по `backend/app/{main,models,data_loader,recommender,explanations,semantic}.py`, `GET /openapi.json` и живому серверу `http://127.0.0.1:8000`. Backend-исходники, CSV, requirements и тесты frontend не меняет.

## Реальный контракт

`GET /api/meta`: `profile_count`, массивы `cities`, `categories`, `event_formats`, `languages`.

`POST /api/recommend`, JSON:

```json
{
  "city": "Алматы",
  "event_date": "2026-10-10",
  "event_type": "корпоратив",
  "category": "Ведущий",
  "budget_kzt": 1500000,
  "duration_hours": 6,
  "language": "русский",
  "limit": 3
}
```

`budget_kzt`: `int`, `gt=0`; `duration_hours`: положительный float либо null; `language`: строка либо null. `limit` отправляется явно как 3. Дата передаётся без timezone-преобразования. Непустые обязательные строки проверяются моделью; окно календаря проверяется обработчиком маршрута. HTTP 422 может содержать массив ошибок FastAPI или строку `detail` для даты вне окна.

| Руководство | Фактический backend | Нормализация frontend |
| --- | --- | --- |
| `/recommend` | `/api/recommend` | Префикс сохраняется proxy |
| `date` | `event_date` | UI `date` → `event_date` |
| `budget` | `budget_kzt` | UI текст → точное положительное целое |
| `duration` | `duration_hours` | Пустое → null; запятая → точка |
| `matches_found` | `matches_found` | `matches_found` |
| `category_not_found` | `no_category_in_city` | `category_not_found` |
| `no_eligible_candidates` | `no_candidates_meet_conditions` | `no_eligible_candidates` |
| `summary` | `message` | Видно над успешной выдачей; для пустых исходов смешанные англоязычные ключи заменены русскими подписями по счётчикам, исходный message доступен в технических деталях |
| `trace.city_category` | `total_category_city` | `trace.total` |
| `trace.eligible` | `eligible_count` | `trace.eligible` |
| `trace.rejected` | `excluded_summary` | `trace.rejected`, без пересчёта |

Ответ содержит также `query` — нормализованный снимок запроса. Адаптер проверяет его совпадение с отправленными условиями.

Карточка: `id`, `name`, `category`, `city`, `price_from_kzt`, `synthetic`, `explanation`, `match_factors: string[]`, `score: number`. `score` не отображается как рейтинг или вероятность. Порядок и объяснения не меняются. Фронтенд отклоняет дубликаты, больше трёх карточек, пустое объяснение, несовместимые типы, несоответствующий город/категорию/цену и противоречивые счётчики.

Языков, календарей, max_hours и полных описаний в карточках API нет. Поэтому проверки этих ограничений выполняются интеграционными тестами по CSV, а не локальной браузерной фильтрацией. Из `match_factors` нельзя восстановить индивидуальные причины отсутствия профиля в top-3.

## Семантика исключений

Полный **first-failure**, реальный порядок из `recommender.py`:

1. `booked` — занят на дату.
2. `over_budget` — стартовая цена выше бюджета.
3. `format` — формат не поддерживается.
4. `language` — запрошенный язык отсутствует.
5. `duration` — превышен max_hours, если он не null.

Каждый профиль учитывается один раз. Проверяется `total_category_city = eligible_count + sum(excluded_summary.values())`. Backend использует Counter: причины без исключений отсутствуют. UI не создаёт отсутствующие строки с нулями. Подходящие за пределами top-3 не считаются исключёнными.

Для success должно быть `len(results) = min(3, eligible_count)` и `eligible_count > 0`. Для двух пустых статусов `eligible_count = 0`, `results = []`; наличие исходной категории различается по `total_category_city` и явному статусу.

## Живые примеры

Полные запросы и ответы всех сценариев, полученные тестами из браузера: [api-examples.json](api-examples.json). Это документация, приложение её не импортирует.

Сценарий B возвращает `matches_found`, `total_category_city=2`, `eligible_count=2`, `excluded_summary={}` и id `HK-39372`, `HK-90001`.

Сценарий C возвращает `no_candidates_meet_conditions`, `total_category_city=10`, `eligible_count=0`, `excluded_summary={"booked":4,"over_budget":6}`. Нельзя утверждать, что все десять были исключены именно по бюджету: первая проверка — дата.

Сценарий D возвращает `no_category_in_city`, нулевые счётчики и пустые results. Основной UI уточняет «в текущем каталоге», так как отсутствие записей не описывает весь рынок города.

## Известные проблемы и действия команды

| Проблема | Воспроизведение / доказательство | Поведение frontend / необходимое действие |
| --- | --- | --- |
| Города разбиты на буквы | `GET /api/meta`: `cities=["А","а","б","е","ж","З","л","м","н","р","с","т","у","ы","ь"]`; `unique_values` выполняет `values.update` над строкой | Только список городов берётся из экспорта реального backend CSV. UI раскрывает источник и отсутствие подтверждённой серверной версии. Команде исправить обработку скалярного `city`; остальные списки API используются напрямую |
| Нет версии каталога | Ни `CatalogMeta`, ни `RecommendationResponse` не содержат хеш/версию | Сравнение учитывает версию, если она появится; сейчас не заявляет доказанную одинаковую версию удалённого сервера. Команде согласовать поле dataset_version и его смысл |
| Нет imputed-флагов | `ContractorCard` не содержит `price_imputed`, `city_imputed` | Не подставляются false и не подмешивается локальный индекс. Команде решить, отдавать ли реальные флаги; UI уже умеет отобразить boolean-предупреждения |
| Объяснения флористов общие | B: HK-39372 и HK-90001, кроме цены, одинаковые общие условия; отличия из описаний не попали в explanation | Тексты сохранены. Команде объяснений улучшить выбор доказательного фрагмента |
| Приветствие вместо специальности | E1/E2: HK-37181 — «ДОРОГУ ОСИЛИТ ИДУЩИЙ… ВСЕМ ПРИВЕТ!» | Текст не переписывается. Команде исключить приветствия и слоганы из содержательного evidence |
| Общие объяснения площадок | F: HK-64395 и HK-90011 содержат условия, но не характерные свойства площадки | Не добавлены выдуманные вместимость/оснащение. Команде использовать исходные подтверждённые признаки |
| Ограничение excerpt в backend | `semantic.description_evidence` обрезает выбранную строку на 180 символах | Frontend показывает всё полученное без дополнительного обрезания; устранение обрыва предложения — задача backend |
| Нет причин по конкретным отсутствующим id | Ответ содержит только агрегированный excluded_summary | При смене даты показаны изменение состава и агрегированная занятость; персональные причины не придумываются |
| Production ещё не развёрнут | Нет публичного адреса | Передать deployment-команде same-origin proxy из frontend README; backend CORS не менялся |

Это замечания к конкретной проверенной версии, не скрытые изменения чужих модулей. Моделей embeddings/LLM в изученном backend нет: `semantic.py` выбирает фрагменты детерминированно по токенам. Frontend не называет себя AI-ранжировщиком.

## Проверка объяснений человеком

- [x] Текст полностью виден на ноутбуке и мобильной ширине, без line-clamp.
- [x] Цена, формат, язык и длительность в просмотренных объяснениях согласуются с запросом и CSV.
- [x] Synthetic не превращён в «проверенный», цена не умножается на часы.
- [x] UI не добавляет характеристики, которых нет в ответе.
- [ ] Убрать имена и сравнить смысл: B/F пока отличаются в основном ценой, содержательной индивидуальности недостаточно.
- [ ] Исключить приветствия и рекламные слоганы: E1/E2 не проходят содержательную проверку.
- [ ] Для каждого source excerpt сохранить законченное предложение; текущий backend имеет срез на 180 символах.

Автоматические тесты проверяют отображение и факты, но их успех не означает прохождение этих содержательных пунктов кейса.

## Безопасные ошибки и состояние

422 сопоставляется с полями по `detail[].loc`; произвольные raw `msg`, `input`, stack и секреты не показываются. 404/405, 5xx, HTML, повреждённый JSON, сеть, таймаут и контракт различаются. Старые карточки скрываются при новом запросе и ошибке. AbortController вместе с номером запроса защищает сброс/новый запрос от запоздалого ответа. История содержит только предыдущий успешный запрос; нет скрытого fallback.
